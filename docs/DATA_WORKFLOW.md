# 数据爬取与迭代更新

## 为什么使用迭代更新

完整净值走势需要历史 `nav_history`。如果每次运行都重新爬取每只基金的完整历史，会非常慢，也容易触发接口限制。

当前逻辑是：

1. 读取上一份完整有效的 `fund_profile_*.json`。
2. 保留每只基金旧的 `nav_history`。
3. 本次只抓最新一页净值。
4. 按日期合并、去重、排序。
5. 保存为新的 `fund_profile_*.json`。

## 首次补全完整历史

如果旧数据里的历史净值不完整，可以在“一键运行”时选择：

```text
补全每只基金的完整历史净值：是
```

这一步会慢很多，但一般只需要做一次。

## 日常更新

日常刷新建议选择：

```text
补全每只基金的完整历史净值：否
```

系统会只补最新净值，速度更快。

## 防止坏数据污染

系统会跳过：

- JSON 格式损坏的数据文件
- 基金数量明显不足的半成品文件

只有数量达到目标基金池 80% 以上的历史数据，才会作为迭代基底。

## 保存方式

新数据先写入：

```text
fund_profile_时间戳.json.tmp
```

写入完成后再替换为：

```text
fund_profile_时间戳.json
```

这样可以降低中途停止导致 JSON 损坏的概率。
